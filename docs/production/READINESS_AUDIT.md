# Queezo production readiness audit

**Review date:** 2026-11-22 (Asia/Manila) · **Baseline:** `main` at `a513c25` · **Recommendation: Hold public launch.**

The checkout has useful security foundations: owner-scoped queries, Argon2id, hashed session tokens, session-bound CSRF protection, private-by-default decks, and regression coverage for several access boundaries. The blockers are the missing production ingress and restore controls, shared SQLite write contention, unbounded storage and inference workloads, and missing operational safeguards. No Critical issue was confirmed. This source and disposable-runtime review does not establish the security of a deployed environment.

### Phase 1 operating limits

- Request bodies: 16 KiB for auth, 64 KiB by default, and about 4.25 MiB for card creation and edits so existing per-side image uploads still fit. API query strings are capped at 8 KiB in the backend. Oversized bodies return HTTP 413, including streamed bodies.
- Storage: 100 decks per account, 150 cards per deck, 12 MiB encoded photos per deck and 64 MiB per account. Per-side uploads remain at 1.5 MiB decoded. Study history has 500 sessions per mode and a combined 192 MiB encoded photo budget per account. Quotas reject growth and do not purge records. Edits that keep or decrease media size remain possible.
- Expensive operations: 6 successful deck copies, 20 Classic starts, and 12 Multiple-Choice starts/retries per account per 15 minutes. Multiple-Choice also allows at most 3 simultaneous preparations per account and 16 globally. Limits report HTTP 429 with a retry hint where applicable. These limits do not implement a durable inference queue.
- For a controlled production pilot, use `AUTH_ENV=production`, `AUTH_COOKIE_SECURE=true`, exact HTTPS values in `AUTH_TRUSTED_ORIGINS`, and leave `AUTH_PUBLIC_SIGNUP=false`. Keep the Compose bind loopback-only. If the default subnet intersects a local network, set `QUEEZO_PROXY_SUBNET`, `QUEEZO_PROXY_DYNAMIC_RANGE`, and `QUEEZO_PROXY_IP` together. The fixed proxy address must be in the subnet and outside the dynamic range. The TLS proxy must forward the original expected Host. Do not expose port 5173 or set wildcard forwarded-header trust.

Existing Compose installs may need the project network recreated once to apply the IP reservation. Stop the project with the same Compose files used to start it, using `docker compose down` without `--volumes`, then start it again with `--build`. This operation is for the deployment operator; the audit and Phase 1 tests did not restart a real project or open its database.

## High findings

### H1 — Public ingress needs explicit HTTPS and trusted proxy configuration

- **Status / blocks public launch:** Confirmed unsafe defaults for Internet exposure. **Yes.** A correctly configured external gateway could provide the missing controls.
- **Location and evidence:** [Compose defaults and published port](../../compose.yaml#L2) and [frontend port](../../compose.yaml#L25) select development auth and publish plain HTTP on all interfaces by default. [Nginx](../../nginx/nginx.conf#L1) listens on port 80 with a catch-all host, no TLS redirect, and no HSTS. [Auth config](../../backend/app/auth/config.py#L18) rejects insecure cookies or HTTP origins in production, but cannot supply encryption or prevent direct HTTP access. [Uvicorn](../../backend/Dockerfile#L11) and [GWA](../../compose.yaml#L44) trust all forwarded headers from reachable peers. [Nginx API proxying](../../nginx/nginx.conf#L9) overwrites incoming client IP headers on API paths, which is protective for direct ingress. Behind a second proxy, the same configuration can collapse all client buckets onto the proxy address.
- **Impact:** Using default Compose directly for public traffic can expose credentials and session cookies in transit. Exposing the backend or admitting untrusted container peers undermines IP-based throttling; an incorrect outer proxy setup can lock out unrelated users.
- **Fix:** Define a fail-closed production deployment using a TLS gateway, exact HTTPS origins, Secure cookies, expected Host enforcement, redirect and HSTS at the edge, and a private or loopback Nginx upstream port. Restrict trusted headers to the proxy hops and isolate Vite, FastAPI, and Ollama from public access. Verify certificate renewal, actual client-IP handling, and public reachability from outside.

### H2 — Login and signup hold the sole SQLite writer during expensive work

- **Status / blocks public launch:** Confirmed transaction scope; saturation impact inferred. **Yes.**
- **Location and evidence:** [Write dependency](../../backend/app/database.py#L128) takes `BEGIN IMMEDIATE` before yielding and holds it through the handler. [Signup](../../backend/app/auth/router.py#L26) and [login](../../backend/app/auth/router.py#L68) keep it through body handling and Argon2 work in the worker pool. [SQLite busy timeout](../../backend/app/database.py#L13) is 30 seconds. [Throttle](../../backend/app/auth/service.py#L104) has IP and email caps but no global admission control; the email bucket can also temporarily deny login for a known account after repeated failures.
- **Impact:** Auth traffic can stall unrelated saves, ratings, presence, and inference snapshot writes. Threads waiting for SQLite may also compete with hash work for worker capacity. Exact saturation thresholds and recovery times are unmeasured.
- **Fix:** Stream or bound input before taking a lock, reserve a throttle slot in a short transaction, bound hash concurrency, and keep verification outside the write transaction. Recheck credential/account state before persisting a session, retain uniqueness and revocation guarantees, and add ingress body/rate/concurrency limits. Benchmark auth traffic alongside legitimate saves in staging.

### H3 — No demonstrated backup and migration rollback process

- **Status / blocks public launch:** Confirmed repository operations gap; external backups and existing data health unverified. **Yes.**
- **Location and evidence:** [Compose volume](../../compose.yaml#L62) puts user data in one named volume. [Startup](../../backend/app/main.py#L23) invokes [schema upgrades](../../backend/app/database.py#L33) including additive DDL, legacy preconditions, trigger installation and backfills. [Profile migration](../../backend/app/profile_migration.py#L6) revisits user rows on startup. [Auth setup](../../AUTH_SETUP.md#L60) records historical manual backups, not a recurring off-host policy or a full restore exercise. [Deck delete](../../backend/app/routers/decks.py#L89) and [cascade models](../../backend/app/models.py#L77) can remove history, and [CLI account deletion](../../backend/app/cli.py#L90) is deliberately permanent.
- **Impact:** Disk/host loss, mistaken deletion, or a failed rollout can affect all accounts, cards and history. Copying only an active WAL database file is not an adequate backup procedure. A startup failure or concurrent migration can prevent service from returning.
- **Fix:** Schedule encrypted, access-controlled, off-host SQLite online backups with retention, monitoring and documented recovery targets. Verify restore, ownership, study counts, foreign keys and integrity on an isolated clone before launch. Use versioned, serialized migrations with preflight, a tested rollback or restore plan, and explicit application startup order. Ensure a restore cannot silently revive revoked sessions; plan a session reset after recovery.

### H4 — Storage, response and write amplification around deck images and history

- **Status / blocks public launch:** Confirmed missing aggregate limits; production resource exhaustion not exercised. **Yes for open signup and media/copy/study features.**
- **Location and evidence:** [Card image limit](../../backend/app/services/card_images.py#L6) is 1.5 MiB decoded **per side**; [deck/card endpoints](../../backend/app/routers/decks.py#L48) cap individual decks at 150 cards but neither cap overall deck storage nor page card reads. [Card serialization](../../backend/app/services/presenters.py#L19) returns inline images. [Share and copy](../../backend/app/routers/community.py#L36) read or duplicate whole decks. [Classic snapshots](../../backend/app/routers/study.py#L34) duplicate photos on every start. [MCQ cache/preparation](../../backend/app/services/multiple_choice.py#L403) also stores photos in question snapshots. [Vue deck loading](../../frontend/src/views/DeckView.vue#L28) fetches the whole collection despite UI pagination. A maximum-sized deck can contain about **600 MiB of base64 image text** across both sides before JSON overhead; this is an upper-bound calculation, not a benchmark.
- **Impact:** High memory, response size, SQLite write time, storage and backup growth. Browser decoding is also exposed to dimension/animation costs: [validator](../../backend/app/services/card_images.py#L27) checks PNG dimensions but only signatures/structure for JPEG and WebP.
- **Fix:** Put server-side quotas on media bytes and deck/session creation. Page responses, serve bounded images separately, enforce pixel and frame limits, and deduplicate snapshot media. Retain history summaries and immutable snapshot references under a documented retention policy. Load-test on synthetic decks and alert on disk headroom.

### H5 — Ollama workload has a serial model slot and no bounded admission queue

- **Status / blocks public launch:** Confirmed design gap; capacity and upstream cancellation unverified. **Yes if public Multiple-Choice generation is enabled.**
- **Location and evidence:** [Session creation and retry routes](../../backend/app/routers/multiple_choice.py#L14) can start work per session without an account/global admission cap. [Worker](../../backend/app/services/multiple_choice.py#L492) tracks in-process tasks and serializes model access with one process-local lock. [Preparation timeout](../../backend/app/services/multiple_choice.py#L24) is 900 seconds and includes time spent waiting. [Generator](../../backend/app/services/distractors.py#L162) validates responses, disables redirects, and caps attempts/time/output tokens, but buffers HTTP responses. [Recovery](../../backend/app/services/multiple_choice.py#L380) marks all unfinished jobs interrupted on startup; multi-worker rollout would share the database but not locks or ownership of jobs.
- **Impact:** Idle or repeated sessions can queue demand and cause unrelated users to time out. Multiple replicas could compete for Ollama or settle another process’s work. The app sends card text to the configured service. Its host exposure, retention and any continued computation after app-side cancellation are unverified.
- **Fix:** Keep one backend worker until job ownership is coordinated. Add bounded queue/admission, per-account and global limits, and monitoring for queue delay, failure and saturation. Use a private, restricted inference endpoint and validate resource limits and restart behavior in staging. Document exactly what student data is sent. Offer Classic or a controlled fallback when Ollama is offline; consider gating AI generation until this passes.

### H6 — Resolved SQLite version needs WAL corruption fix verification

- **Status / blocks public launch:** Dependency exposure risk. Installed upstream version falls in the affected range; vendor patch status for the exact package and occurrence in Queezo are unverified. **Yes until the release image has a verified fix.**
- **Location and evidence:** [Floating Python image](../../backend/Dockerfile#L1), [WAL and pooled connections](../../backend/app/database.py#L13), [WAL initialization](../../backend/app/database.py#L41), and [shared GWA volume](../../compose.yaml#L44). The audit image reported SQLite **3.46.1**, Debian package **3.46.1-7+deb13u2**. The [SQLite WAL-reset notice](https://www.sqlite.org/wal.html#the_wal_reset_bug) describes rare corruption when WAL connections write/checkpoint concurrently and identifies 3.51.3 and named backports. The version string alone cannot rule out another distro backport.
- **Impact:** If unpatched, rare interleavings can corrupt the shared file. This is distinct from ordinary write contention and from proven corruption.
- **Fix:** Pin a release image with provenance for an upstream fix or verified backport. Record the package revision/digest and validate migration, checkpoint, backup and restore on that image. Do not attempt to induce corruption on existing data.

## Remediation order and launch checklist

1. **Contain exposure first (H1, H5).** Put staging behind the intended HTTPS ingress. Verify host rejection, exact origins, Secure cookie flags, auth redirects, no-store, forwarded identity, and closed backend/Vite/Ollama ports. Gate public inference and use an invite-only rollout until limits are demonstrated.
2. **Protect existing data (H3, H6).** Select a patched SQLite build. Produce an encrypted off-host backup, perform a fresh restore and upgrade rehearsal, compare counts/ownership/history, run integrity and foreign-key checks, and demonstrate a rollback path and recovery times.
3. **Bound abuse and load (H2, H4, H5, M3).** Shorten auth write scope, add queue/account/storage budgets, page card responses and bound media, then verify controlled concurrent usage. Rehearse rate limits behind the real proxy and failure of Ollama, including Classic availability, cancellation and restart.
4. **Make releases and incidents observable (M2, M4–M6).** Add mandatory CI for frontend/backend tests, migration checks and browser smoke flows; scan the release image digests and dependencies. Confirm redaction, retention, alerts and on-call ownership. Verify critical availability with functional probes from outside the host.
5. **Verify privacy and usability (M1, M3, M7, L1–L2).** Exercise two synthetic accounts and a guest through owner CRUD, Classic and MCQ progression, public/unlisted/private link transitions and copies, profiles/friends, signup/login/logout, recovery and account deletion. Confirm privacy wording, log policy and operational moderation. Keep real records out of test fixtures.
