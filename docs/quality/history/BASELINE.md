# Phase 4B.1 Multiple-Choice performance

Historical record. See [Multiple-Choice performance](../PERFORMANCE.md) for current benchmark entry points.

This benchmark exercises Queezo's production preparation worker, owner-scoped SQLite cache, Ollama generator and hybrid fallback in an isolated process. It uses temporary SQLite databases and synthetic users. It measures the service path and excludes browser rendering, HTTP polling between the browser and FastAPI, and timer or grading flows.

## Workload

Each deck contains 10, 50 or 150 distinct synthetic arithmetic prompts and integer answers. The prompt template is fixed, and card order, model seed and option shuffling use seed 42. A new study session is created for each measurement. Deck membership and content stay the same across each size's three runs.

| Scenario | Cache and generator configuration |
| --- | --- |
| Cold | Empty SQLite distractor cache. Every card calls the generator and successful sets populate the cache. Cold refers to SQLite. Ollama's model residency is allowed to carry across runs and reported load times are recorded. |
| Warm | Reuses the cache generated by the preceding cold run. The runner asserts that all cards hit the cache and no Ollama request occurs. |
| Hybrid | Keeps the even zero-based card positions in cache and evicts the odd positions. Two-fifths of the deck use the assigned transport. On positions 1, 11, 21 and so on, a scripted connection error forces real same-deck fallback. |
| Two cold sessions | Starts two 10-card sessions for separate synthetic owners and decks in the same preparation worker. The worker has its existing one-slot lock. No extra Ollama parallelism or workers are configured. |

Live mode sends real requests to local Ollama except for the explicit hybrid outage slots. Mock mode runs with networking disabled. The fixture waits 30 ms per response and makes the first response for positions ending in 3 repeat the correct Back to trigger a retry. Mock times are control-path timings under the scripted response delay, and they provide no model speed estimate.

## Measurements

- **Preparation** runs from enqueue to completion of the production worker. Scenario wall time also includes session creation. A card's latency starts when its iteration begins, includes wait for the model slot and ends after committing its question or failure. P95 uses nearest rank. Initial queue time for cards not yet selected is reflected in total preparation and first-ready timings.
- **First 1 and 5** are elapsed times from enqueue to commit of those ready question snapshots. This is internal readiness. The current UI opens questions after the full session becomes active.
- **Cache and generation** count actual lookup hits and misses. Bench-only instrumentation counts live HTTP calls, scripted failures, retries, peak overlapping requests, requests using the model, and new entries with deck-derived choices. Generator wall time includes the model call, retries and local validation. The raw HTTP measurements include Ollama's reported duration and load duration when available.
- **Database** counts SQL statements and sums cursor execution durations under SQLAlchemy. This includes cursor time awaiting SQLite locks where applicable. The measurement excludes ORM row materialization, transaction commits, connection setup and thread-pool scheduling. Warm wall time is a better measure of the full cache-and-snapshot path than cursor time alone.
- **Resources** record Python process CPU time and sampled peak RSS for each scenario. The process high-water mark in the raw report is cumulative. The Windows runner also samples Ollama process CPU counters and working sets at roughly 500 ms intervals. Summed working set can count shared pages twice. Host CPU is based on observed counter deltas for PIDs sampled at least twice within the scenario window. A subsecond run may leave no usable host CPU measurement. Ollama's process working set and its model residency on the GPU are separate measurements.

## Reproduce

From the repository root in PowerShell 7, use the dedicated benchmark image and write new reports. Keep only one live run active at a time to avoid competing for Ollama.

~~~powershell
& ./docs/quality/run-performance.ps1 -Mode mock -OutName performance-mock-rerun
& ./docs/quality/run-performance.ps1 -Mode live -OutName performance-live-rerun
# Isolate a 150-card cold rerun
& ./docs/quality/run-performance.ps1 -Mode live -Sizes 150 -ColdOnly -OutName performance-live-150-cold-rerun
~~~

To align the host samples with the scenario times and produce smaller summary files:

~~~powershell
$quality = Join-Path (Get-Location) 'docs/quality'
docker run --rm --network none --mount "type=bind,source=$quality,target=/quality" queezo-perf-backend python /quality/summarize_performance.py /quality/results/performance-live-rerun.json --samples /quality/results/performance-live-rerun-host.csv --out /quality/results/performance-live-rerun-summary.json
~~~

Live mode uses the installed `qwen3:1.7b` model at local port 11434. The script builds a separate image, starts a disposable container and mounts only the quality directory for results. Raw output includes a per-card latency and request trace. The run is seeded for comparability while hardware contention, model residency and runtime differences can still change timings and responses.

The run used an Intel Core i5-13420H (8 physical cores, 12 logical processors), 15.64 GiB of host RAM, Windows 11 build 26200 and an NVIDIA RTX 3050 Laptop GPU with 6 GiB of VRAM. Docker 29.9.2 ran under WSL2 with 12 logical CPUs and 7.58 GiB of available RAM. The backend used Python 3.12.16, SQLite 3.46.1 in WAL mode, and one preparation worker. Ollama 0.40.16 used `qwen3:1.7b` with a 4,096-token context. It reported about 1.59 GiB of model residency, all on the GPU. The generator used version 2, JSON mode, disabled thinking, at most 3 requests and a 60-second timeout per request. The preparation deadline was 900 seconds.

## Verification

All 96 generator, cache and Multiple-Choice backend regression tests passed. Both complete suites produced all 10 expected scenarios. Checks on the reports covered readiness order, cache proportions, fallback provenance, and a one-request concurrency ceiling.

## Bottlenecks and optimization priorities

1. **Reduce cold generation work.** At 150 cards, the generator accounted for 95% of cold wall time. Warm cache completed in 1.783 s with no inference calls. Hybrid took 39.437 s with 60 live requests versus 150 cold. Cache coverage and avoiding repeated generation have more leverage than tuning individual SQL statements.
2. **Investigate contention around the shared model slot.** The pair remained serial at the model and added a 562.1 ms median slot wait. Source reads and cache checks also run under that slot. A subsequent bounded benchmark can compare scheduling policies and confirm that hits can avoid waiting behind generation before considering more in-flight model calls.
3. **Profile fixed work in the warm path.** Warm 150 still executed 1506 preparation statements, with only 62.0 ms in cursor execution. The timings justify profiling snapshot writes, ORM work, commits and thread-pool boundaries separately before choosing a SQLite optimization.

These are single measurements of a short, homogeneous workload on one machine. Real decks with longer prompts, repeated answers or more retries can take longer. The Phase 4A quality findings remain applicable. The synthetic benchmark recorded internal ready snapshots without changing the existing activation rule.
